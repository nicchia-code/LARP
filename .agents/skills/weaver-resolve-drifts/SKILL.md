# Weaver: resolve Drifts

You resolve the **open Drifts** the instruction names. A Drift records that the code and the **Model** (with its **Requirements**) disagree. The developer decides, Drift by Drift, whether the code changes or the Model and Requirements do; you ask them, record the decision in one **resolution Proposal**, and hand it over. The developer's approval of that Proposal is what resolves the Drifts. You never change the code here.

## Hand-over

A new Proposal starts as a **Draft**, not approvable. Finish its Drift list and every file, then run `weaver proposal move <id> open` without `weaver proposal show` before it: read the changes in the hand-over's output. If they do not match what you meant, reopen the Proposal with `weaver proposal edit <id>`, fix it, and hand it over again. If the hand-over is refused, fix the reported problems and hand it over again. Only after it succeeds tell the developer to review it, and stop. Before every later change, call `weaver proposal edit <id>` again: it returns an open Proposal to Draft, so hand it over again when finished.

## Announcing cards

Announce a Proposal as soon as you know you will write it: `weaver announcement new --input -` with `{"kind":"proposal","title":"<title>"}` prints an announcement ID. Pass it when you open that Proposal: `weaver proposal new --input -` with `{"title":"<title>","kind":"resolution","announcement":"<id>"}`. The Board shows a ghost of the card meanwhile. Never wait for the ghost to show and never skip or delay a card because of it; an unknown ID is only noted in the output.

## Hard rules

- This skill runs only when the instruction of a Weaver job names it. Without that instruction (Chat, Ask more, or any other conversation that is not a job) do not follow it, announce nothing, ask no round and open no Proposal. In Chat a Proposal starts as a design request sent with `weaver request new`.
- NEVER edit `.weaver/model/` or `.weaver/requirements/` directly, nor the generated `weaver-req-*` skills. Every change goes through a Proposal.
- Agents may approve, reject or discard a Proposal, decide a Drift or delete a Task in To do (`weaver task delete`) only when the developer explicitly asks for that decision in the conversation. Without that request, do not decide and do not ask the developer about it: stop and tell them the decision is theirs, on the Board. A request to prepare a resolution does not by itself authorise any of them.
- NEVER change the code of the project, and never create Tasks: approving the resolution creates the Task of each Drift to be fixed in the code.
- Never apply a recommendation for a Drift the developer skipped, and never decide a Drift on your own.

## Naming cards

Every live Proposal, Task and Drift has a temporary **short number** (`P3`, `T3`, `D3`) besides its **permanent identity** of eight characters.

- Name cards to the developer by short number and title, for example "Drift D2 – title", also in the final report. A closed card has no number: use its permanent identity.
- In every command you run and every file you write use **only the permanent identity**, taken from `--json` (field `id`; the number is the field `number`) or from the file or folder name. **Never write a short number in a file**: it changes from one working copy to another.
- Give every card you create, and its announcement, a **short title**: at most five words, about 40 characters, a name for the card rather than a sentence describing the work (for example "Ghost text" instead of "Describe the start screen and guide written requests with a ghost text"). Put the detail in the body, even when the title loses information. Only the title of an announcement is checked (one line, at most 60 characters). Titles that a skill composes from another title stay as they are.

## Notes on the job

The developer follows the work through notes: `weaver job edit --input -` with `{"note":"<one line>"}`, passed as `weaver job edit --input - <<'JSON'`, the object and `JSON`. Declare a note at the start of each stage of the work: reading the Drifts, the round of questions, writing the resolution, handing over. Write 3 to 6 notes for the whole job, never one per command. A note is one sentence of at most 120 characters (a longer one is cut) saying what the agent does and why, for the developer: no first person, no `weaver` command names and no short numbers of cards, in the language of the instruction when it asks for one (for example "Explores the order Machine before asking the first questions"). A note changes nothing else and is never needed to deliver a card.

## Language

When the instruction asks for a language, the texts listed below go in that language. Without a language in the instruction, nothing here changes.

- **In the language of the instruction:** the titles and bodies of Tasks; the titles, bodies and Fix options of Drifts; the titles, bodies and reasons of Proposals; the text, context and options of questions; the notes of the job and the titles of announcements; the titles, summaries and texts of History entries; the replies during the work and the final report.
- **Always in English**, whatever the language: the whole Model (the name of the System; the names of Features, Machines, Actors and States; IDs and Event names; the descriptions in Model files); the Requirements (Areas, titles and bodies of fragments); the Specs, also their `notes`; code and its comments, commit messages and the project's own documentation; the headers Weaver reads in files (`States`, `Events`, `General`, `What happens`, `What should happen`, `Where in the code`, `Fix options`, `Already present`), the `(initial)` and `(final)` markers and the front matter fields; technical terms (commands and tools such as `git pull` or `npm install`, names of products, services, libraries and languages) and Weaver's own terms (Proposal, Task, Drift, Board, Run, Scan). Weaver's interface and the `weaver` command line stay in English.
- **A language changes nothing already written.** When you edit a file written in another language, keep its existing text and write only the new or rewritten text in the chosen language; never translate the whole file.
- **No first person in Weaver's texts.** In what you write for Weaver (questions, contexts and options of rounds, titles and bodies of Proposals, Tasks and Drifts, History entries), Weaver is always "Weaver" and you are "the agent": no first-person pronouns or first-person verbs, in any language. Your replies in the conversation are not Weaver's texts and do not change. Text already written is not rewritten.

## Steps

The instruction has one of four forms: it names a Drift to resolve (follow the Steps, asking the developer); it names a Drift and says the developer already answered its prepared question, with the answer (follow "The answer is already given"); it asks to rework a rejected Proposal on the Drifts it names (follow "Reworking a rejected resolution"); or it asks to refine a stale Proposal on the Drifts it names (follow "Refining a stale resolution").

1. **Read the Drifts.** For each Drift the instruction names (and only those), run `weaver drift show <id>` (add `--json` for structured data; `weaver drift list --json` gives the creation order). It shows the two sides, the **Fix options**, the Model references and the attached Proposal with what it changes. Read that Proposal too, with `weaver proposal show <id>`. A recurring Drift, one with `previous` (always a list) in `weaver drift show <id> --json`, has a chain of predecessors: run `weaver drift show <previous-id> --json` on each of them in turn, from the nearest to the farthest, to get its identity, title and decision taken. A named Drift that is no longer open is left out; say so in the report. Stop, without asking anything, if none is left.
2. **Explore.** Read the Model and the code each Drift concerns: `weaver model show <ref>` (a Machine `<id>`, a State `<machine/State>`, an Event `<owner.EVENT>`), `weaver model list --input -` with `{"text":"<word>"}` in a heredoc, and the code that implements them. Facts are your job: never ask the developer what the Model, the Requirements or the code can tell you.
   **With sub-agents**, hand this exploration to them, at most N at once, where N is the limit in the instruction ("Run at most <N> sub-agents at once"): one Drift (or a few that concern the same thing) each, with the commands above and the instruction to come back with a short account of what the Model says, what the code does, which Fix option fits and what the attached Proposal would change. A sub-agent asks the developer nothing and writes no Proposal. You alone ask and write. **Without sub-agents**, explore yourself, one Drift after the other.
3. **Ask once**, as described in "Asking" below: one single-choice question per Drift, in creation order.
4. **Decide from the answers.** Per Drift, from the chosen option:
   - a **Fix option** → `fix-code`, with that option's number (from 1, as listed by `weaver drift show`) and the answer's free text as the note, if any;
   - a Drift **without Fix options** (it always has an attached Proposal) → the developer chose either **adopt the changes of the attached Proposal** (`proposal`: the resolution carries them as below) or **close without changing anything** (`dismissed`). Correcting the code is not a choice: when the free text asks for it, whatever the choice, the decision is `fix-code` with no `option` and the free text as the note;
   - the **behaviour the code already has** → the Model and the Requirements must say so, so the decision is `proposal` and the resolution carries the changes to them. When the Drift has an attached Proposal, those are its changes, rewritten on the current Model if it has gone stale, adjusted by the free text; when it has none, they are what you work out from the Drift and the free text, and when the Model and Requirements already say it, nothing needs to change and the decision is `dismissed`;
   - a skipped question → no decision: the Drift stays out of the resolution and open.
5. **Write the resolution.** `weaver proposal new --input -` with `{"title":"<title>","kind":"resolution","body":"<why>","announcement":"<id>"}`, in the language of the instruction (the title stays in English when the instruction asks for none). The body says what is resolved, in a line per Drift with its short number and title and the decision, in domain words, and lists nothing else. Record the decisions with `weaver proposal edit <id> --input -` and `{"drifts":[{"drift":"<drift-id>","decision":"proposal|dismissed|fix-code","option":<n>,"note":"<text>"}]}`: one call may carry several decisions, and `removeDrifts` takes the ids of Drifts to take out; `option` and `note` go only with `fix-code`. For the `proposal` decisions, edit the files as `weaver-design` does (`weaver proposal edit <id> --input -` with `{"edit":["<model-path>","requirements/<area>/<fragment>.md"]}` prints the path to write for each, the complete new version of each file; `{"delete":[…]}` removes files), following its FORMAT.md, and change nothing the decisions do not require.
   With many Drifts, split them into Proposals that build on each other (open the later ones with `requires` of the earlier ones' ids, and announce them as above), each Drift in exactly one of them. Keep Drifts whose Model changes touch the same files in one Proposal.
   Give each Proposal a short title (see Naming cards).
6. **Check the output.** Hand each Proposal over (step 7) without `weaver proposal show` before it: the hand-over's output reports the checks, and the changes and the Drift list it prints must match the answers, and nothing else. When it warns of a Requirement fragment larger than 12 KB that the resolution writes into, split that fragment in the same Proposal before handing it over, as `weaver-design` says under "Good Requirement habits": cut where it suits the project, give every new fragment a name and a description that say when it is needed, and move the sections without changing their text.
7. **Hand over.** Run `weaver proposal move <id> open` (the earlier ones first) only after step 6; if refused, or its output does not match the answers, reopen it with `weaver proposal edit <id>`, correct it, and hand it over again. Then report, in domain terms: the Proposals with their decisions per Drift, the Drifts left open because their question was skipped or because they were no longer open, and tell the developer to review the resolution on the Board or with `weaver proposal show <id>`. Stop. Do not approve it, reject it or resolve any Drift.

## The answer is already given

This applies when the instruction says "The developer already answered its prepared question:" followed by a one-line JSON `{"selected":[…],"text":…}` (the `selected` labels and the optional free `text`). Then:

- Do not open a round and never run `weaver question new`: the JSON is the answer of the round for this Drift.
- Do steps 1, 2, 4 and 5 of "Steps" for that Drift only, with that answer as the answer of the round: decide from it as step 4 says (the `selected` label names the option of the prepared question, which `weaver drift show --json` lists in `prepared`) and write the resolution as step 5 says.
- Hand it over as step 7 says and report.

## Reworking a rejected resolution

When the instruction says to rework the rejected Proposal `<id>` with the developer's feedback on the Drifts `<d1>`, `<d2>`, follow the Steps for exactly those Drifts, with these changes:

- Read the rejected resolution with `weaver proposal show <id>` (body, decisions per Drift, files and `## Feedback`). Its decisions count as already taken, except what the feedback changes or leaves in doubt. Without `## Feedback`, redo the same resolution on the Model as it is now.
- The round of step 3 is optional: ask one round only for the Drifts whose decision the feedback opens or leaves open, as in "Asking"; Drifts whose decision stands are recorded again without a question. A named Drift that is no longer open stays out, as step 1 says.
- Write the resolution again from scratch, on the Model as it is now, without requesting the rejected one. Pass `"reworks":"<id>"` in the `weaver proposal new` of the resolution it opens (with several Proposals, only the first); Weaver links it only when the named Proposal is rejected and no other one already reworks it, otherwise it creates it unlinked and the result says why.
- After the hand-over, tell the developer to review the new resolution. Never approve, reject or discard it, or resolve any Drift, yourself.

## Refining a stale resolution

This section applies when the instruction says to refine the stale Proposal `<id>` on the current Model and Requirements, on the Drifts `<d1>`, `<d2>`. Without that sentence, skip it. The Steps (reading, exploring, round of questions, new Proposal) do not apply, except where this section sends you back to them.

Refining reworks the same resolution. It keeps its identity, short number, place on the Board and the Proposals that require it. You work only on the open Drifts the instruction names. You never approve it. At the hand-over Weaver decides where it goes: a resolution attached to a Drift always goes back Open, and the developer accepts it again from the Drift; a resolution blocked by a required Proposal that is not approved yet goes back Open with its reasons; otherwise Weaver approves it (or waits for the end of a Run first).

1. **Read what the Proposal changes.** Run `weaver proposal show <id>`: it gives the body with the decisions per Drift, the stale files and their differences from the files as they are now. Then read only the current Model and Requirements of those stale files, and `weaver drift show` of the named Drifts only when a decision needs it. Do not read the code, announce nothing and file no Drift: the Proposal already exists.
2. **The decisions already taken for those Drifts stay.** The developer answered them in the resolution: record them again without a question. Ask nothing yet: a decision that the current Model contradicts and that you cannot choose yourself goes into the single round of step 4, asked after the rebase (see "Asking"), as one single-choice question for that Drift. Decide everything else, and write each such decision in the body as an assumption.
3. **When the current Model already has the whole change of the `proposal` decisions,** reconcile nothing. Ask one round with one question that explains which approved Proposal already contains the change, with two options: `Remove` (description: "Reject this Proposal: the current Model already has its change.") and `Keep` (description: "Leave it as it is, to refine; nothing changes."), recommended `Keep`. Name that Proposal to the developer by its short number and title.
   With `Remove`, reject it: `weaver proposal move <id> rejected --input -` with `{"feedback":"Already in the current Model."}`, in a heredoc. That is the developer's decision, taken in the round, and the only case in which you reject a Proposal.
   With `Keep`, or when the round is skipped or lost, stop and change nothing.
4. **Otherwise, reconcile the Proposal with the current Model.** Run `weaver proposal edit <id> --input -` with `{"rebase":true}`: the Proposal goes back to Draft and is marked `refining` until you hand it over again. The rebase drops the rows of the Drifts that are no longer open (the Drifts of the instruction are the ones that remain) and the broken entries of `requires` (required Proposals that were rejected, discarded or are missing, and, in a cycle, only this Proposal's own entry), and lists each one in its output. Adapt the resolution without them. Then, when a decision of step 2 needs the developer, or something of a dropped Proposal was needed and you cannot choose yourself, ask one single round of `weaver question new` with all those questions; never a second round, and no round at all when nothing is needed.
   Rewrite in full, on the current Model, each Model and Requirement file of the `proposal` decisions, as the current file plus the change, never removing what other approved Proposals changed. The `fix-code` and `dismissed` decisions need no files. Keep in the body one line per Drift with its decision, and add one line for each thing the refinement changed.
5. **Hand over and stop.** Run `weaver proposal move <id> open`, as step 7 says. If the hand-over is refused (invalid Model, a missing or unusable decision, code fixes that cannot be applied, a missing label), correct what it reports with `weaver proposal edit <id>` and hand over again. Never approve, reject or discard the Proposal, or resolve any Drift, yourself.
6. **A Draft left half-way through a refinement** (still marked `refining`) resumes from there: reread its files, reconcile again as in step 4 if it is stale again, and go on.

## Asking

Make **one round only**, with one question per Drift, in the order the Drifts were created, all single-choice (`multi: false`), run as "Asking" of the other skills describes: **`weaver question new --input -`** with the JSON request on standard input, in a heredoc.

- Send one complete round as `{"questions":[...]}`. Every question has an `id` that is the permanent identity of the Drift it asks about (so each Drift is named once), `question`, `options` as `{label, description}`, a zero-based `recommended` index, and an explicit `multi` boolean. Two fields are optional: `context` on a question and `details` on an option; when present they must not be blank.
- Keep `question` short: one sentence that reads on its own. Put the background of the Drift in `context`, the tradeoff in a few words in `description`, and the pros and cons of each option in `details`. `question`, `context`, `description` and `details` are Markdown; labels are plain text. Do not supply "Other": Weaver always offers a free-text answer.
- The developer sees only the round (each question, its context, its options and their own answers), never your conversation. Make every question self-contained: it says everything needed to decide, with no references to the conversation or to another question, and no first person (write "Weaver" or "the agent"). Omit `context` when the question and the options are enough on their own.
- The question presents the situation in the words of the domain. The options say what could happen: one for each Fix option of the Drift and one for the behaviour the code already has, all written the same way, without saying which option is what the code does today. A Drift without Fix options has exactly two options instead, listed in this order: adopting the changes of its attached Proposal (index `0`, the recommended one) and closing without changing anything. `recommended` is your own choice, except for such a Drift, where it is adopting the attached Proposal.
- For a recurring Drift, `context` lists the chain of its predecessors, from the nearest to the farthest, each with its identity, title and decision taken (`fix-code` with the title of the chosen option, `proposal` or `dismissed`), so the developer sees that the earlier decisions did not close the difference. Name each predecessor by its permanent identity: a resolved Drift has no short number.
- The result is JSON on stdout. With `status: "answered"`, `answers` is keyed by question id: each entry is `{"status":"answered","selected":[<labels>],"text":<optional free text>}` or `{"status":"skipped"}`. The free text of a question goes with the choice: with a Fix option it becomes the note; with the behaviour of the code it guides you when you write the changes to the Model; for a Drift without Fix options, when it asks to fix the code it becomes the note of a `fix-code` with no option. A skipped question is an explicit developer skip: apply no recommendation, leave that Drift out of the resolution, so it stays open, say so in the report, and do not ask it again.
- When the round is finished, open the resolution at once, without asking the developer to confirm a summary.
- With `status: "unavailable"`, Weaver cannot show questions: ask in no other way, open no resolution, and tell the developer. When the developer says to continue, run the same `weaver question new` again: it is a new round.
- An error `interrupted` or `cancelled` (exit 1) stops this work at once: do not open or hand over any resolution from partial answers or recommendations, do not retry or resume the round; tell the developer that the questions were lost.
- An error `invalid-input` (exit 2) means the request was refused before opening a round: correct the field it names and submit the corrected request. A usage error is never unavailability.
- **Wait for `weaver question new` to finish**: it blocks until the developer answers, however long that takes. Run it with bash `timeout: 0`, never a fixed value. Never use a timer, `sleep`, periodic reads of the output or interval checks; never end the turn to be woken up; never treat the command as failed and never run it again.
- Never use omp's own question tool, and never write the questions in the conversation: `weaver question new` is the only way to ask the developer.

## Prepared question

Every job that files a Drift prepares in advance the question the developer would be asked about it, so Resolve opens at once. This section says how a prepared question is written (the other skills point here).

### Writing a prepared question

Explore the Drift as step 2 of "Steps" says, with the same limit of sub-agents (read the Drift with `weaver drift show <id>`, its attached Proposal with `weaver proposal show <id>`, the Model and the code it concerns), but **ask the developer nothing and write no resolution**: you only record the question. Write one single-choice question (`multi: false`) for the Drift, in the language of the instruction, with these parts:

- `id`: the permanent identity of the Drift. `question`: one short sentence that reads on its own. `context`: the background of the Drift in the words of the domain; for a recurring Drift (`previous`, a list, in `weaver drift show <id> --json`) every chain of its predecessors, from the nearest to the farthest, each with its permanent identity, title and decision taken.
- `options`, as `{label, description}` (and `details` when useful), all written the same way, without saying which one is what the code does today: one for each Fix option of the Drift, in their order, and one for the behaviour the code already has. A Drift **without Fix options** has exactly two options instead: adopting the changes of its attached Proposal (the recommended one) and closing without changing anything.
- `recommended`: your own choice, except for a Drift without Fix options, where it is adopting the attached Proposal.
- **A Drift from a merge** (`merge` is `true` in `weaver drift show <id> --json`: the scan after a merge found it in the files the merge brought). Its prepared question always has the option for the behaviour the code already has, with the decision `proposal`: keep the code and adapt the Model and the Requirements. That decision is written with its attached Draft (or Open Proposal), passed as `proposal` in the same `weaver drift edit`, and the option is the recommended one (`recommended` is its index), with or without Fix options. Any Fix options stay, in their order, the first listed first, and none is preselected. A preparation without that option, or recommending another one, is refused with the reason, and a question already prepared follows the same rule.

Each option carries its decision, in `decisions`, one entry per option in the same order: `{"decision":"fix-code","option":<n>}` with the number of the Fix option (from 1, as `weaver drift show` lists them), `{"decision":"proposal"}` or `{"decision":"dismissed"}`. The option for the behaviour the code already has is `proposal` when the Model or the Requirements must change to say it, and `dismissed` when they already say it and nothing needs to change. A `proposal` decision needs a Proposal attached to the Drift: when the Drift has none and the behaviour of the code needs one, write a Draft with `weaver-design` (without its interview, `weaver proposal new --input -` with the changes to the Model and the Requirements, not handed over) and pass its identity as `proposal` in the command below. Without Fix options, the options are `proposal` (the attached Proposal) and `dismissed`.

Record it with `weaver drift edit <id> --input -` and `{"prepared":{"question":{…},"decisions":[…]},"proposal":"<id>"}` in a heredoc (`proposal` only when you attach a Draft in this command). The command checks the Drift is open, the question and the decisions; a refusal names each problem: fix it and run the command again. The question is valid only while the Model and the Requirements of the Drift's references do not change.

## Sub-agents context sharing

When you hand a part of the work to a sub-agent, in whatever way your agent starts sub-agents, you pass it what you have already read that concerns its part, so it does not look for it again and does not read it again.

- **What you pass.** Of what you have already read, only what concerns that sub-agent's part, plus a short common part (the request and the decisions, when there are any): Weaver's texts quoted as they are (the written request with its images put in words, the output of `weaver model show`, `weaver task show`, `weaver drift show`, `weaver proposal show`, the decisions of the interview) and the places in the code already known, one line per reference, ``- `<ref>` — <where in the code>``. Never code, never everything you gathered, and nothing you read only to pass it on.
- **What the sub-agent does.** It does not reread the Weaver texts it received and reads on its own only the ones that are missing. It always reads the code, also at the places it received, always runs the commands that register its work (`weaver task move <id> doing`, `weaver task new`, `weaver drift new`) and loads its skill as without this feature. A received place that no longer matches the code is ignored: it searches by itself. Context sharing never stops a job.
- **What comes back.** Each sub-agent reports where it found the code of what it saw, one line per reference as above; you reuse those lines in your own work and for the sub-agents that follow.
- **Limits.** No sub-agent runs again a read-only `weaver` command for a text it received, and what you pass to each one concerns only its part: never copy into every sub-agent all that you gathered.

In this skill, the exploration of step 2 and the preparation of a question give each sub-agent, for each of its Drifts, the output of `weaver drift show`, the Proposal attached to it (`weaver proposal show`), the chain of its `previous` Drifts and where the code is. The code at its Where in the code is read again before deciding.

## Command reference

Every `weaver` command, with its verbs and input fields, is in [COMMANDS.md](../weaver-design/COMMANDS.md), generated from the command registry. `weaver <object> <verb> --help` prints the usage, the fields with their types and limits, an example and the output fields.

## PowerShell

The examples use POSIX syntax. In PowerShell, pass JSON with a pipe and `--input -`, for example `Get-Content -Raw round.json | weaver question new --input -`, instead of `<` or a heredoc. On Windows PowerShell 5.1, set `$OutputEncoding` and `[Console]::OutputEncoding` to UTF-8 first, or non-ASCII characters arrive as `?`. Never pass the JSON as the text of `--input`: Windows PowerShell 5.1 strips the inner quotes of arguments to external programs.
