# Weaver: implement

You implement **Tasks** so that the code behaves as the **Model** says and is built as the **Requirements** say. The Model wins. If following it or a Requirement is impossible, or you discover it is wrong or incomplete in an important way, you **stop working on that Task** and file a **Drift**: you never silently deviate and you never edit the Model or the Requirements. The Drift blocks the Task and the other Tasks that concern the same thing. Asked for one named Task, you stop there and take no other. Asked for the runnable Tasks, you hand them out to sub-agents as places free up and go on: the Drift leaves its Task in Doing, and `weaver task list` with `runnable` skips the Tasks it blocks.

## Hand-over

A new Proposal starts as a **Draft**, not approvable. Finish every file, then run `weaver proposal move <id> open` without `weaver proposal show` before it: read the changes in the hand-over's output. If they do not match what you meant, reopen the Proposal with `weaver proposal edit <id>`, fix it, and hand it over again. If the hand-over is refused, fix the reported problems and hand it over again. A Proposal meant for a Drift is attached to that Drift when the Drift is filed, before it is handed over, so it never shows up alone. Only after it succeeds tell the developer to review it. Before every later change, call `weaver proposal edit <id>` again: it returns an open Proposal to Draft, so hand it over again when finished.

## Announcing cards

When you know you must file a Drift (see "When you must file a Drift"), announce it before you write it up: `weaver announcement new --input -` with `{"kind":"drift","title":"<title>"}` prints an announcement ID. Pass it when you file the Drift: `weaver drift new --input -` with `announcement` set to it; if the Drift carries a Proposal, announce only the Drift and pass the same ID to `weaver proposal new --input -` (field `announcement`) too. A sub-agent announces the cards it files exactly as you do. The Board shows a ghost of each card meanwhile. Never wait for a ghost to show and never skip or delay a card because of it; an unknown ID is only noted in the output.

## Hard rules

- NEVER edit `.weaver/model/`, `.weaver/requirements/` or the generated `weaver-req-*` skills.
- Agents may approve, reject or discard a Proposal, decide a Drift or delete a Task in To do (`weaver task delete`) only when the developer explicitly asks for that decision in the conversation. Without that request, do not decide and do not ask the developer about it: stop and tell them the decision is theirs, on the Board. A request to implement Tasks does not by itself authorise any of them.
- Every question to the developer goes through `weaver question new`, as "Asking" below says, waiting rules included: never with your own question tool, and never as a round written in the conversation.
- NEVER implement behaviour that contradicts the Model, or code that contradicts a Requirement, to get something working.
- Do not touch code unrelated to the Task.

## Naming cards

Every live Proposal, Task and Drift has a temporary **short number** (`P3`, `T3`, `D3`) besides its **permanent identity** of eight characters.

- Name cards to the developer by short number and title, for example "Task T3 – title", also in the final report. A closed card has no number: use its permanent identity.
- In every command you run and every file you write use **only the permanent identity**, taken from `--json` (field `id`; the number is the field `number`) or from the file or folder name. **Never write a short number in a file**: it changes from one working copy to another.
- Give every card you create, and its announcement, a **short title**: at most five words, about 40 characters, a name for the card rather than a sentence describing the work (for example "Ghost text" instead of "Describe the start screen and guide written requests with a ghost text"). Put the detail in the body, even when the title loses information. Only the title of an announcement is checked (one line, at most 60 characters). Titles that a skill composes from another title stay as they are.

## Notes on the job

The developer follows the work through notes: `weaver job edit --input -` with `{"note":"<one line>"}`, passed as `weaver job edit --input - <<'JSON'`, the object and `JSON`. Declare a note at the start of each stage of the work: each group of Tasks, the final check and the History. Write 3 to 6 notes for the whole job, never one per command. A note is one sentence of at most 120 characters (a longer one is cut) saying what the agent does and why, for the developer: no first person, no `weaver` command names and no short numbers of cards, in the language of the instruction when it asks for one (for example "Explores the order Machine before asking the first questions"). A note changes nothing else and is never needed to deliver a card.

A sub-agent that implements a Task writes none.

## Language

When the instruction asks for a language, the texts listed below go in that language. Without a language in the instruction, nothing here changes.

- **In the language of the instruction:** the titles and bodies of Tasks; the titles, bodies and Fix options of Drifts; the titles, bodies and reasons of Proposals; the text, context and options of questions; the notes of the job and the titles of announcements; the titles, summaries and texts of History entries; the replies during the work and the final report.
- **Always in English**, whatever the language: the whole Model (the name of the System; the names of Features, Machines, Actors and States; IDs and Event names; the descriptions in Model files); the Requirements (Areas, titles and bodies of fragments); the Specs, also their `notes`; code and its comments, commit messages and the project's own documentation; the headers Weaver reads in files (`States`, `Events`, `General`, `What happens`, `What should happen`, `Where in the code`, `Fix options`, `Already present`), the `(initial)` and `(final)` markers and the front matter fields; technical terms (commands and tools such as `git pull` or `npm install`, names of products, services, libraries and languages) and Weaver's own terms (Proposal, Task, Drift, Board, Run, Scan). Weaver's interface and the `weaver` command line stay in English.
- **A language changes nothing already written.** When you edit a file written in another language, keep its existing text and write only the new or rewritten text in the chosen language; never translate the whole file.
- **No first person in Weaver's texts.** In what you write for Weaver (questions, contexts and options of rounds, titles and bodies of Proposals, Tasks and Drifts, History entries), Weaver is always "Weaver" and you are "the agent": no first-person pronouns or first-person verbs, in any language. Your replies in the conversation are not Weaver's texts and do not change. Text already written is not rewritten.
- **Self-contained Tasks.** The body of a Task is understood without the conversation that produced it: it says what must be true when done, with the conditions and consequences as the Model says them, and every decision of the interview that concerns it, because whoever implements it does not see that conversation.

## Advisor Scanner

The Run does not scan: omp's advisors check the code against the Model during the run instead.

- **Advisor notes.** When the advisor finds that the code of a Task departs from the Model, the Requirements or the Task, it sends a note. Correct that code before moving the Task to Done; do not file a Drift for it.
- **Drifts from the advisor.** The advisor files a Drift only for code outside the Tasks of this Run. Such a Drift has no origin (no `task`): it blocks every Task not Done that concerns the same thing. A Task already In progress that it blocks is not stopped: finish it, and the Run goes on with the others.
- **Sub-agents.** A sub-agent that implements a Task has the advisor too; it does steps 2 to 5 for its Task as below.

## Steps

1. **Pick the Tasks.** Asked for one named Task (the instruction says "on Task <id>"), use the ID you were given, and do steps 2 to 5 for it. Asked for the runnable Tasks, the instruction gives the `weaver task list` command to run, with `runnable`, `max` and `groups` and, for a group of Tasks by model, `proposals` or `notProposals`. Run it as it gives it, passing the JSON with `--input -` and a heredoc (`weaver task list --input - <<'EOF'`, the JSON, `EOF`) and changing nothing but `max`. `max` is the number of sub-agents the instruction allows, an integer of 1 or more. With `groups`, it prints `## Group <n>` blocks (with `--json`, `groups`, each with its `tasks`): each group holds runnable Tasks that concern the same thing, directly or through other Tasks of the group, or name the same project file; `max` counts groups; each group lists at most 3 Tasks, in order. It skips the blocked Tasks, moves nothing, and recomputes the answer each time, so a Task that waited for the Task fixing its Drift comes back, after it, once that Task is Done.
   - **With sub-agents**: start one sub-agent for each free place, up to N at once, in whatever way your agent starts sub-agents, and give each one a group. Start the sub-agent `weaver-implementer` (defined in `.omp/agents/weaver-implementer.md`): its prompt carries steps 2 to 5 of this skill, so do not tell it to read this skill or to run those steps. Give it the permanent identities of the Tasks of the group, in order, and each Task's images as paths, which it looks at before it starts (never put an image in the text of the instruction). Give it the sentences of the instruction that concern a sub-agent, on the same line, as the instruction writes them: the language sentence, if the instruction has one; and the texts you already read that concern its Tasks, as "Sub-agents context sharing" says. The prohibitions hold for it and its prompt repeats them: it never runs `weaver task list`, never takes a Task it did not receive, never runs the full suite, the linter or the build, and never scans; it runs the commands that register its own work, and when one of its writes is stopped by a file reservation (a file held by another sub-agent) it stops at once, does not undo its changes, leaves its Task in Doing and comes back with what it did, the file and the sub-agent that holds it. It comes back with each Task done, closed without changes with its note, or the Drift it filed. Each time a sub-agent comes back, its place is free: step 5 says what to do next. Never write a file that a sub-agent holds: a write of yours stopped by a file reservation waits until that sub-agent is done.
   - **Without sub-agents**, or with one place only: do steps 2 to 5 yourself for each Task, one after the other, running the same command with `max: 1` before each.

   Read a Task once, with `weaver task show <id>`. That text is the Model and the Requirements for this Task. A Machine reference includes the State tree and the Events with who receives them. A State reference includes the outgoing Transitions, including those inherited from the States that contain it, marked as inherited. An Event reference includes the Transitions that react to it. A reference to a whole Area includes the text of every section. Under `## Requirements` are the Requirements attached to the referenced elements, and every General section that has text, written in full. A Technical Task references no Model element; implement it as a normal engineering task from the Requirements in that text.

   **Images.** When the Task has images (the `Images` block of `weaver task show`, the `images` field with `--json`), they are part of what the Task needs. Implementing it yourself, look at them before you start. Handing the Task to a sub-agent, pass it the paths and tell it to look at them before it starts, opening them with the tool it reads files with. Never put an image in the text of the instruction. An image you cannot see is ignored silently.
2. **Start it.** `weaver task move <id> doing`. If the move is refused because the Task is blocked, nothing changed. Asked for one named Task: stop, take no other Task, and report the Task and the Drift (or fix Task) the refusal names; only the developer can decide on that Drift. In a run over several Tasks `weaver task list` with `runnable` never names a blocked Task, so a refusal means something changed since you asked: leave that Task and go on with the other Tasks you were given.
3. **Read the code.** The Model and the Requirements for this Task are the `weaver task show` text already read. Read the code that implements them and follow its conventions. For this Task, do not run `weaver model show`, and do not open a `weaver-req-*` skill. If a Transition the Task must implement does not appear in that text, run one `weaver model show <ref>` for that Transition, and do not resume the tour.

   **Code notes.** A Task whose text ends with `## Code notes` (written by a design, a scan or a compare, never a fix Task) gives you a place to start from: where to look, the conventions, the pitfalls and what can be reused, with the commit the code was read on. Begin from the notes, not from nothing.
   - Run `git diff <commit> -- <files>` once on the files the notes cite, with the hash of their `Commit:` line, against the files on disk.
   - A cited file that did not change is not explored again: of those, read only the ones you change, before changing them. A cited file that changed is explored again as for a Task without notes.
   - Without a `Commit:` line, outside a git repository or with a commit git does not know, every cited file counts as changed: start from the notes all the same.
   - Any file is read before it is changed, cited or not.
   - A note that contradicts the code is ignored and that part is explored as for a Task without notes; it is no Drift. The report says which note was wrong.

   The notes are hints, never part of what must be true: the text above them is. A Task without `## Code notes`, and every fix Task (which rereads its Where in the code), is implemented as before.

   **Check the premise first, for a fix Task.** A Task that fixes a Drift says so on its Column line (`from Drift <id>`), and its text carries the Drift's two sides and its Where in the code. Before writing any code, re-read the code at Where in the code and at the Task's references, and compare what it does with What happens. If it already does what What should happen says (the Model or the Requirement), change nothing: run `weaver task move <id> done --input -` with the JSON `{"unchanged":"<note>"}` in a heredoc, the note saying what you checked (the code and the behaviour); this also dismisses the Drift. Then skip steps 4 and 5 for that Task, and list it in the report's closed-without-changes list. Otherwise continue with step 4. A Task with no Drift skips this check.
4. **Implement.** Write the code, including every Transition's condition and consequence exactly as the prose in the Task text says, and the States around it that the Task depends on. Follow every Requirement in that text, including the General sections written there. Add or update tests for the behaviour. While writing, run the tests added or changed for this Task and the existing tests of the behaviour this Task changes. Do not run the project's full suite, the linter or the build after the Task. After the code, do not read the Model again.
5. **Finish the Task.** `weaver task move <id> done`. Record the permanent ID of each Task this run moves to Done without `unchanged`; the History of step 7 names them. In a run over several Tasks, each time a sub-agent (or you, without sub-agents) finishes its group (Done, closed without changes, stopped by a Drift, or stopped by a file reservation as step 1 says), run the same `weaver task list` command with `max` set to the free places (N minus the sub-agents still working) and start the groups it prints at once, from step 1. When it says no Task is runnable and no sub-agent works, the Tasks are finished: go on to step 6. A Task whose sub-agent was stopped by a file reservation stays in Doing, unfinished: once the sub-agent has come back, release it with `weaver task move <id> todo`, so that the command above offers it again after the Task that holds the file is Done.
6. **Check the run.** A Task asked by name is its own run, so this step follows it at once. In a run over several Tasks, this step runs once, after the last Task, when no sub-agent works and the command of step 1 says no Task is runnable; never in a sub-agent. Run the project's checks (tests, type check, linter and build) together, as parallel processes, that do not depend on each other, and wait until every one has finished before judging the check: it passes only when all of them pass. Two checks depend on each other when one uses what the other produces or when both write the same files; when in doubt, run them one after the other. If the check fails, fix the code and run again, together, the checks that failed and those that depend on them, without reading the Model again; leave every Task in the column it is in. If you cannot tell which Task broke the check, say so in the report and stop.
7. **Write History.** Run this step after step 6, whenever the run moved at least one Task to Done without `unchanged`, also when the check of step 6 failed. Read the entries with `weaver history list --json`, and `weaver history show <id> --json` for those that look related. Group the Tasks of this run by macro-feature, reading their titles, bodies, their Proposals (`weaver task show <id> --json`) and the entries already written: when an entry already tells the same feature, update it with `weaver history edit <id> --input -` and `{"tasks":["<id>"],"commit":{"files":["<path>"],"message":"<message>","checksFailed":false}}` (it may also change `title`, `summary` and `body`; `tasks` only adds Tasks, never removes one) instead of writing another; otherwise write a new one with `weaver history new --input -` and `{"title":"<title>","summary":"<text>","body":"<text>","tasks":["<id>"],"commit":{"files":["<path>"],"message":"<message>","checksFailed":false}}`, listing in `tasks` every Task it names. Name every Task this run moved to Done without `unchanged` at least once, by its permanent ID; a Task closed without changes is never named. Write title, summary and body in the language the instruction asks for; the title is one line, the summary one line of at most 280 characters. A refused command changes nothing and names each problem: fix it and run it again. Only the main agent writes entries: a sub-agent never writes them, and a run interrupted before this step writes none.
   - **Pass `commit`** with every `history new` and with every `history edit` that adds Tasks, whether Atomic commits is on or not; an edit that adds no Task needs none. `files` are the files of the code that you and your sub-agents created, changed or removed for the Tasks of that entry and no others, relative to the project root with `/` and without repeats, taken from what you and the sub-agents reported (the list may be empty). `message` is a commit message in English: its first line says in at most 72 characters what the feature does, optionally followed by a blank line and a body. `checksFailed` is `true` when the final check of step 6 failed; the entry is written all the same. A path outside the project, ignored by git, or missing and not tracked by git refuses the whole command: fix the list and run it again.
   - **Never run `git add` or `git commit` yourself.** When the developer turned Atomic commits on, Weaver commits the files, and the command prints `Committed <hash>.` or `Not committed: <reason>.`; a commit that cannot be made never undoes the entry. Keep each entry that was not committed, with the reason printed, for the report of step 9.
8. **Prepare the questions of the Drifts.** Follow "Preparing the questions" below, before the report.
9. **Report.** Say what you implemented, in domain terms, the Drifts you filed (each with its Task), anything you noticed that was outside the Tasks, the Code notes that contradicted the code (which note, of which Task), the Tasks closed without changes, each with its note in a list of its own, the Tasks still in To do left unrun, each with the Drift or the fix Task that blocks it, as the last `weaver task list` with `runnable` lists them, the History entries you wrote or updated, each by its title, and, in a list of its own, each entry that was not committed, with the reason the command printed.

## When you must file a Drift

Stop working on the Task at once and file a Drift when any of these is true:

- The Model cannot be implemented as written (contradiction, impossible condition, an Event nothing can emit).
- The Model is silent on a case that the Task forces you to handle, and the choice changes what the user sees or what data is kept.
- Doing the Task right requires a State or Transition the Model does not have.
- A Requirement cannot be followed (it conflicts with the Model, another Requirement, or the platform), or the Task forces a construction choice the Requirements should decide and do not.

Before running `weaver drift new`, re-read the code at the place you name in `where` and file only if it really does what `happens` says. A Drift the developer dismissed, whose text has not changed since, is never filed again; a difference closed by a fix of the code or an accepted Proposal stays closed while the Model or the Requirement there still says the same thing. A Drift dismissed by its own fix Task (closed without changes) does not count as closed, so a difference that comes back is filed again.

Then:

1. Decide which case applies. If the code is right and the Model forgot a case, begin a Proposal with the `weaver-design` skill, without its interview (list your choices in the Proposal body): `weaver proposal new --input -` with `{"title":"<title>","body":"<why>","label":"<short label>","announcement":"<id of the Drift's announcement>"}`. Finish its files, but do not hand it over yet: attach the Draft to the Drift in step 2, then hand it over right after with `weaver proposal move <id> open`; if the hand-over is refused, correct it and hand it over again. Otherwise there is no Proposal, except in the case of step 2 where no fix respects both the Model and the Requirements.
2. File the Drift **once**: `weaver drift new --input - <<'JSON'` and `JSON`, with the object `{"title":"<title>","refs":["<nearest Model element or Requirement>"],"task":"<id of the Task you are implementing>","happens":"<what the code does or what you would do instead, in terms of behaviour>","should":"<what the Model or Requirement says and why it cannot be followed>","options":[{"title":"<title of the way you recommend>","text":"<what it changes and costs>"},{"title":"<title of another way>","text":"<…>"}],"where":"<where in the code>","announcement":"<id>"}` (up to five options), adding `"proposal":"<id of the Draft>"` only in the first case. The two texts, the options and `where` are required; `where` is the only place for code locations. Write them as described in "Writing a Drift". `task` records the origin: the Drift blocks that Task and Tasks that concern the same thing.
   Give the Drift a short title (see Naming cards).
   - **Resolved Drifts first.** Before filing, run `weaver drift list --input -` with `{"all":true,"refs":["<ref>"]}` for the references of the difference. If it is back after a fix of the code or an adaptation of the Model, set `previous` to the ID of that resolved Drift; the command refuses a previous Drift that is open or unknown. When `task` names a fix Task (one whose `drift` field is set), Weaver writes `previous` itself, so it is not needed.
   - **No fix respects both.** When no fix of the code respects the Model and the Requirements together (for example, two Requirements contradict each other), file the Drift with no `options`, with `proposal` set to the Draft that repairs the Model or the Requirements, as in step 1. A Drift without Fix options is refused without a Proposal.
3. Leave the Task in Doing; the developer decides whether the code or the Model changes. Asked for one named Task, stop here. In a run over several Tasks, go on with the free places as step 5 says. The Drift blocks only the Task it was filed for and the Tasks that concern the same thing, and `weaver task list` with `runnable` skips those.
4. Report. Say what you implemented and the Drift you filed, with the Task it concerns. In a run over several Tasks this goes into the final report described in step 9. A sub-agent reports to the main agent instead, which writes the one final report.

Small choices that stay below the level of the Model's States, Transitions and Events and that no Requirement covers (names, data structures, how an effect is carried out) are yours to make; do not file Drifts for them.

## Writing a Drift

The developer reads a Drift at a glance, as a programmer, but not as a code review. Write the two sides, and the fix options, at the level of behaviour.

- **Say what the System does and what it should do**, in the words of the domain ("the cart total ignores the coupon"), not how the code does it.
- **Name no variable, function, class, field or file** in `happens`, `should` or the options, unless the difference cannot be understood without it. Then name only the one or two that matter, as `inline code`.
- **Code locations go only in `where`**, which is required for every Drift: the files, and the code element when it helps. Re-read that code before filing; no line numbers, which go stale, and no long pieces of code.
- **Give two to five fix options**, the one you recommend first: each option is an object `{"title":"<title>","text":"<text>"}`. Each is a different way to reach what should happen, not a step of one plan, and says in terms of behaviour what changes and what it costs. About 60 words each, short Markdown, no headings or tables inside an option. Titles differ. A Drift filed with fewer than two, more than five, or an option missing its title or text is refused.
- **Fix options reach what should happen** without changing the Model or any Requirement, and respect every Requirement that applies to the elements of the Drift, not only those it names. An option that asks for an exception to, or a change of, the Model or a Requirement is not a fix option: that way goes to a Drift with a Proposal.
- **Use short Markdown:** short paragraphs, a bulleted list when there are several separate points, **bold** for the one or two terms that carry the difference. No headings inside a section, no tables, about 100 words per side.

## Parallel execution

This section is for the main agent of a run over several Tasks that can start sub-agents. For a Task asked by name, or without sub-agents, skip it and follow the steps as written.

- **Ask.** Before the first Task, run the command of step 1: it prints groups, `max` counts groups, and the largest group comes first. The runnable Tasks that concern a Task In progress that the Run has taken are held back and sit in no group.
- **One group, one sub-agent.** Each group goes to one `weaver-implementer` sub-agent, with at most 3 of its Tasks, in the order the command prints them. Never keep more than N sub-agents working, the ones already working included: a group being worked takes one place. A Task the sub-agent reports unstarted goes to a new sub-agent, with the summary of the first, as soon as a place is free. For each Task it finished, the sub-agent reports the files of the code it created, changed or removed; step 7 uses them.
- **Limits.** Never start a blocked Task (`weaver task list` names none among the runnable ones), and never start a Task before the Tasks it waits for are Done.
- **Revise.** Ask again with `max` for the free places when a sub-agent comes back (Done, closed without changes or stopped by a Drift), when a new runnable Task is born (for example a fix Task) and when a Task becomes blocked.
- **Conflicts.** The file-reservation rule of step 1 holds in every Run. When a sub-agent comes back stopped by a file reservation, or by seeing that its Task changes the same files or the same behaviour as another Task In progress, it does not undo its changes and never corrects files that belong to another Task's work. Free its place and release the Task as step 5 says; when the Task that holds the file is Done, the command offers the stopped Task again, and a new sub-agent takes it with the report of the first one.
- **Report.** The report of the run (step 9) says which Tasks were stopped by a file reservation or held back, and why.

## Asking

Run **`weaver question new --input -`** with the JSON request on standard input, in a heredoc, for every round of questions. It is the only way to ask the developer: never use omp's own question tool and never write the questions in the conversation.

- Send one complete round as `{"questions":[...]}`. Every question has a unique non-empty `id`, `question`, `options` as `{label, description}` (2 to 5 of them), a zero-based `recommended` index, and an explicit `multi` boolean. Two fields are optional: `context` on a question and `details` on an option; when present they must not be blank.
- Keep `question` short: one sentence that reads on its own. Put the background of the decision in `context`, the tradeoff in a few words in `description`, and a longer explanation, only when it is needed, in `details`. `question`, `context`, `description` and `details` are Markdown; labels are plain text. Set `multi: true` only when several answers can genuinely hold together. Do not supply "Other": Weaver always offers a free-text answer.
- The developer sees only the round (each question, its context, its options and their own answers), never your conversation. Make every question self-contained: it says everything needed to decide, with no references to the conversation or to another question, and no first person (write "Weaver" or "the agent"). Omit `context` when the question and the options are enough on their own.
- The result is JSON on stdout. With `status: "answered"`, `answers` is keyed by question id: each entry is `{"status":"answered","selected":[<labels>],"text":<optional free text>}` or `{"status":"skipped"}`. A skipped question is an explicit developer skip: use its recommendation for that decision, report it as an assumption for review, and do not ask it again.
- With `status: "unavailable"`, Weaver cannot show questions: ask in no other way, file no Drift and write no History, and tell the developer. When the developer says to continue, run the same `weaver question new` again: it is a new round.
- An error `interrupted` or `cancelled` (exit 1) stops this work at once: no partial answers, no recommendations, no retry, no fallback, no resuming of the round; tell the developer that the questions were lost.
- An error `invalid-input` (exit 2) means the request was refused before opening a round: correct the field it names and submit the corrected request. A usage error is never unavailability.
- **Wait for `weaver question new` to finish**: it blocks until the developer answers, however long that takes. Run it with bash `timeout: 0`, never a fixed value. Never use a timer, `sleep`, periodic reads of the output or interval checks; never end the turn to be woken up; never treat the command as failed and never run it again.

## Preparing the questions

At the very end of the work (before the final report) prepare the question of every Drift this work filed, so Resolve opens at once. You alone do this, never a sub-agent that compares or implements.

1. **Find the Drifts.** Run `weaver drift list --input -` with `{"currentJob":true,"unprepared":true}`; never read `WEAVER_JOB` by hand: the command reads it itself. It lists the open Drifts of this job, the advisor's included, with no valid prepared question and outside every resolution. When it lists none, skip the rest.
2. **Prepare each.** Follow "Writing a prepared question" in the `weaver-resolve-drifts` skill (read it first) for each Drift, with the sub-agents you have: hand the exploration to at most N of them at once (N is the limit in the instruction), one Drift (or a few that concern the same thing) each, and have each record its question with `weaver drift edit`. Without sub-agents, one Drift at a time. A sub-agent asks the developer nothing and registers no other card.
3. **Report.** The final report says how many Drifts were prepared and which were not (with the reason).

## Sub-agents context sharing

When you hand a part of the work to a sub-agent, in whatever way your agent starts sub-agents, you pass it what you have already read that concerns its part, so it does not look for it again and does not read it again.

- **What you pass.** Of what you have already read, only what concerns that sub-agent's part, plus a short common part (the request and the decisions, when there are any): Weaver's texts quoted as they are (the written request with its images put in words, the output of `weaver model show`, `weaver task show`, `weaver drift show`, `weaver proposal show`, the decisions of the interview) and the places in the code already known, one line per reference, ``- `<ref>` — <where in the code>``. Never code, never everything you gathered, and nothing you read only to pass it on.
- **What the sub-agent does.** It does not reread the Weaver texts it received and reads on its own only the ones that are missing. It reads the code itself, also at the places it received, as step 3 says for a Task with Code notes: a file the notes cite and the code did not change since their commit is not explored again, and every file is read before it is changed. It always runs the commands that register its work (`weaver task move <id> doing`, `weaver task new`, `weaver drift new`) and loads its skill as without this feature. A received place that no longer matches the code is ignored: it searches by itself. Context sharing never stops a job.
- **What comes back.** Each sub-agent reports where it found the code of what it saw, one line per reference as above; you reuse those lines in your own work and for the sub-agents that follow.
- **Limits.** No sub-agent runs again a read-only `weaver` command for a text it received, and what you pass to each one concerns only its part: never copy into every sub-agent all that you gathered.

In this skill:

- **Implementing a Task.** A sub-agent receives the text of `weaver task show` when you have already read it, with the `## Code notes` it carries, and the places in the code already known. A `weaver-implementer` sub-agent loads no skill, and it skips `weaver task show` only when it received that text. Every sub-agent still takes the Task with `weaver task move <id> doing`.
- **Preparing the questions.** For each Drift, pass the output of `weaver drift show`, the Proposal attached to it, the chain of its `previous` Drifts and where the code is. The code at its Where in the code is read again before deciding.

## Command reference

Every `weaver` command, with its verbs and input fields, is in [COMMANDS.md](../weaver-design/COMMANDS.md), generated from the command registry. `weaver <object> <verb> --help` prints the usage, the fields with their types and limits, an example and the output fields.

## PowerShell

The examples use POSIX syntax. In PowerShell, pass JSON with a pipe and `--input -`, for example `Get-Content -Raw round.json | weaver question new --input -`, instead of `<` or a heredoc. On Windows PowerShell 5.1, set `$OutputEncoding` and `[Console]::OutputEncoding` to UTF-8 first, or non-ASCII characters arrive as `?`. Never pass the JSON as the text of `--input`: Windows PowerShell 5.1 strips the inner quotes of arguments to external programs.
